# 组批量管理与数据管理改进方案

> 状态：核心已实现（待发布） · 基于 v0.7.5 · 2026-11-22

## 1. 目标

- 让组数量多起来以后仍然能高效整理：批量合并、合并到、删除、导出、改色
- 保持“组 = 一次导入形成的归档容器”这个核心抽象不被破坏
- 合并导出不修改本地数据，不创建持久化的临时组
- 明确本地隐私边界，避免“上传/下载”文案让用户误以为数据经过服务器

## 2. 非目标

- 不做“复制组”：重复导入同一个文件已经等价于复制，且复制需要重映射会话/文件 ID、占用双倍存储
- 不做“解散”独立动作：解散就是合并到默认组，不再增加第二个概念
- 不做嵌套组、标签体系：这些是未来的独立维度，不塞进组
- 不把多个真实组合并后长期保留为一个组作为默认推荐；合并是显式操作，不是整理常态

## 3. 现状与问题

### 数据管理现状

设置 → 数据管理目前有三项：

1. 导入历史对话：选择一个 ZIP/JSON，导入为一个新组
2. 导出所有历史会话：所有会话合并为一个 DeepSeek 兼容 ZIP
3. 删除所有对话：清空本地会话、组、附件

组操作目前只能在侧栏逐组进行：重命名、配色、合并、移入默认组、导出、删除。

### 需要解决的问题

- **组多了以后只能逐个操作**，缺少多选和批量出口
- **“导出所有历史会话”不保留分组**：所有会话混成一个归档，重新导入只会得到一个组
- **全量导出不带扩展 sidecar**：摘要、系统提示词、引用/思考状态不会恢复
- **合并组会丢组级附加信息**：现有单组合并只移动会话并删除源组，源组的 `extras` 直接消失
- **“上传”按钮误导**：实际只是选择本地文件，没有网络上传
- **默认组规则需要统一**：批量操作中默认组不能作为合并/删除的源，但可以作为合并目的地

## 4. 概念与语义

- **组**：一次导入形成的归档容器，同时承担文件夹、来源、导出单位和附加信息载体
- **默认组**：无主会话的兜底容器；可改名、配色、导出、参与合并导出，但不可作为合并/删除的源，可作为合并目的地
- **合并到…**：选中的非默认组 → 会话和附加信息并入已有组，或在目的地列表底部新建一个组；源组删除
- **新建空白组**：不经过导入直接创建一个空组，用于先建目录、再拖入会话
- **默认组作为目的地**：即旧说法里的“解散”；不单独提供“解散”按钮
- **合并导出**：只读操作，把选中的组在内存中组装成一个虚拟组导出，原组不变
- **全量导出**：所有会话合并为一个兼容 ZIP，不保留分组；与组批量管理不重复

## 5. 入口与界面

入口：设置 → 数据管理 → “组批量管理”。

弹窗结构：

- 顶部：标题、组数量、已选组数 / 会话数
- 工具栏：全选、仅选普通组、取消选择、新建空白组
- 列表：复选框、颜色点、组名、会话数、附加信息条数、来源名
- 底部固定操作栏：
  - 合并到…
  - 导出
  - 改色
  - 删除
- 破坏性操作使用危险色，并在确认框中显示影响范围
- 首期入口只在设置 → 数据管理；不在侧栏另加“管理组”入口
- 默认组不满足条件的按钮使用 `aria-disabled` + 灰样式，**不要用原生 disabled**，点击时弹出 `defaultGroupLockedHint` 对应的多语言提示

全选规则：

- 主复选框全选所有组，包含默认组，支持半选状态
- “仅选普通组”一键排除默认组，方便直接合并
- 如果以后加搜索/筛选，全选只作用于当前筛选结果，并在按钮上标明

## 6. 选择与默认组规则

| 操作       |     最少选择 | 默认组作为源 | 默认组作为目标 | 说明                         |
| ---------- | -----------: | ------------ | -------------- | ---------------------------- |
| 合并到…    | 1 个非默认组 | 禁止         | 允许           | 目标列表排除已选组；可新建组 |
| 删除组     | 1 个非默认组 | 禁止         | 不适用         | 确认框显示组/会话数          |
| 分别导出   |       1 个组 | 允许         | 不适用         | 只读                         |
| 合并导出   |       1 个组 | 允许         | 不适用         | 只读，虚拟组                 |
| 批量改色   |       1 个组 | 允许         | 不适用         | 默认组也可改色               |
| 新建空白组 |       不适用 | 不适用       | 不适用         | 只创建空组，不改动现有组     |

补充：

- 合并到…时，目标列表 = 未被选中的组 + 默认组 + “新建组”入口
- 不允许“目标同时是源”，避免会话先移动又被删除的歧义
- 默认组被选中时，“合并到… / 删除”整体禁用，而不是只排除默认组继续操作
- 所有保护必须在 store 层再校验一次，不能只靠按钮置灰

## 7. 操作定义

### 7.1 合并到…（含新建组）

- 复用单会话“移动到组”的目的地列表 UI：颜色点 + 组名，底部是“新建组”输入框
- 选择一个已有组：会话移入目标组，源组删除
- 选择“新建组”：输入组名（必填）后，先创建组再执行合并；创建与合并应作为一个操作完成
- 目标列表 = 未被选中的组 + 默认组；不允许目标同时是源
- 源组的附加信息并入目标组，去重规则同第 8 节
- 目标组自己的名称、颜色、来源保持不变
- `sourceName` 保持原义（创建该组时的导入文件）：合并进已有组不改目标组的 `sourceName`，合并创建的新组留空；不要把多个来源文件拼进这个字段
- 如果以后要在 UI 展示合并来源，另加可选 `mergedFrom: string[]`；首期不做
- 至少选择 1 个非默认组；默认组不可选为源

### 7.2 删除组

- 删除组及其中的会话、会话元数据、无引用附件
- 确认框必须显示：
  - 将删除 N 个组
  - 将删除 M 个会话
  - 将删除 K 条组级附加信息
- 不提供“只删组、保留会话”选项；需要保留会话时使用“合并到默认组”
- 默认组禁止删除
- 不做回收站/撤销；删除前确认是最后一道防线

### 7.3 分别导出

- 每个选中组生成一个独立文件
- 格式选项与现有“导出为…”一致：DeepSeek 兼容 ZIP、对话浏览器扩展 ZIP、Claude JSON
- 组级附加信息、扩展字段按所选格式处理
- 组数量多时提供进度状态；多个文件逐个保存，浏览器可能拦截连续下载，需要提示
- 默认组可以导出

### 7.4 合并导出

- 选中组在内存中组装为一个**虚拟组**，不写入 IndexedDB
- 格式选项与现有“导出为…”一致：DeepSeek 兼容 ZIP、对话浏览器扩展 ZIP、Claude JSON
- 可编辑导出组名，默认预填本地时间 `合并导出 YYYY-MM-DD HH-mm-ss`（文件名安全，避免 Windows 不支持的冒号）；时间精确到秒，连续导出不会重名
- 会话顺序、组名、附加信息写入扩展 sidecar（选择扩展格式时）
- 原组的名称、颜色、附加信息、会话归属完全不变
- 默认组可以参与
- 失败时只影响导出，不产生任何本地数据变更

### 7.5 批量改色

- 选中的组统一设置颜色，可选“无颜色”
- 默认组可参与
- 只修改 `group.color`，不触碰会话和附加信息

### 7.6 新建空白组

- 入口放在组批量管理弹窗工具栏（标题旁或列表上方）
- 输入组名后直接创建，复用现有 `createGroup`
- 新组默认为无色、无来源，可被勾选，也可作为合并目的地
- 不改变当前勾选；创建成功后刷新列表并提示
- 侧栏以后可以再加一个“+”入口，但不要和弹窗入口同时首期实现，避免重复

## 8. 组级附加信息（extras）策略

### 问题

Claude 的 `projects.json` 项目提示词、`users.json` 记忆等，会存进 `group.extras`，在组菜单“附加信息”中展示。当前单组合并直接删除源组，会把这些内容一起丢掉。批量合并会放大这个问题。

### 原则

- **绝不静默丢弃**
- 合并后，源组 extras 全部进入目标组
- 先按 `title + content` 去重
- 同一标题但内容不同：保留多条，并在标题或说明中标注来源组
- 列表和确认框显示 extras 数量，让用户知道会合并/删除多少条
- 合并导出时，虚拟组包含合并后的 extras
- 删除组时，确认框明确提示 extras 会一起删除

### 实现建议

新增纯函数，例如：

```ts
mergeGroupExtras(sources: SessionGroup[]): { title: string; content: string }[]
```

规则：

1. 完全相同的 `title + content` 只保留一条
2. 标题相同、内容不同：保留两条，标题追加来源组名，例如 `记忆（来自 A）`
3. 来源组名重名时用序号/组 ID 兜底，避免标注歧义

先修复现有 `mergeGroups` 的丢 extras 问题，再做批量合并。这个修复可以独立提交。

## 9. 全量导出：保留名称，改说明

名称保持“导出所有历史会话”，按钮仍可下载 ZIP，但小字说明必须准确：

中文建议：

> 将全部历史会话合并为一个 ZIP，包含本地图片原件；其他附件仅保留文件信息。**不保留分组、组级附加信息，也不包含扩展导出字段。** 文件在本机生成，不会上传。

英文对应：

> Combines all chats into one ZIP with locally stored images; other attachments keep file details only. Group structure and group-level extras are not preserved. The archive is generated locally and never uploaded.

后续如需真正的“完整备份”，单独设计保留组结构、extras、扩展字段的备份格式，不与全量导出混用。

## 10. 本地隐私文案与图标

术语已确定统一为“导入 / 导出”，不再使用“上传 / 下载 / 打开归档”描述本地数据处理：

- 设置 → 数据管理导入按钮：`导入`
- 设置 → 数据管理全量导出按钮：`导出`
- 侧栏与欢迎页入口：`导入归档`
- 发布包/Release 资产仍用“下载”，因为它指从网络获取安装包，与本地数据导入导出无关
- 导入/导出说明明确“文件只在本机读取/生成，不会上传”
- 图标可以继续使用上传/下载箭头，但文案不再制造服务器语义
- 不写“零网络请求”：应用仍会请求 GitHub API 检查更新，应表述为“对话数据不会上传”

## 11. 架构与实现约束

- 批量选择状态只存在弹窗内，不持久化
- 合并导出使用**内存虚拟组**，不创建临时数据库组，不产生清理逻辑
- 批量修改操作（合并、删除、改色）应尽量使用单个 IndexedDB 事务；失败时不能出现“源组已删、目标没写完”的半完成状态
- store 层统一校验默认组规则：合并源、删除源禁止默认组；合并目标允许默认组
- 操作成功后递增 `dataVersion`，刷新搜索索引；如果当前会话被删除，切回欢迎页
- 删除组与会话时复用现有的附件引用计数清理逻辑
- 批量导出复用现有 `exportArchive`，新增组选择/虚拟组参数，不复制导出逻辑

- 增加“数据只在本机处理”提示

- 设置 → 数据管理 → 组批量管理

- 默认组可参与

- 合并到…（含新建组；默认组可作目标）
- extras 去重与来源标注

- 新建空白组

### Phase 3：批量删除

- 影响范围确认
- 原子删除与附件清理

## 13. 测试清单

- 全选 / 半选 / 仅选普通组
- 默认组被选中时，合并和删除按钮灰显，点击出现对应语言提示
- 默认组可作为合并目的地
- 目标列表不包含已选组
- 合并到已有组后源组消失、会话归属正确
- 合并到新建组后组创建成功、源组消失、会话归属正确

- 相同 extras 去重；同标题不同内容保留并标注来源
- 删除组会删会话和无引用附件，不影响其他组的同名附件
- 合并导出后原组、会话、extras 完全不变
- 合并导出包含合并后的 extras 和扩展字段
- 全量导出说明与实际行为一致
- 导入/导出文案不出现“上传到服务器”的暗示

## 14. 待定问题

- 分别导出选择 Claude JSON 时，多个文件逐个保存还是额外包成外层 ZIP
- 完整备份的字段范围与恢复语义（见第 15 节）
- 合并来源 `mergedFrom` 是否需要首期实现并写入扩展 sidecar

## 15. 完整备份（暂缓）

完整备份不是给其他 AI 助手读取的导出，而是本应用的状态快照，解决“浏览器数据被清空/换设备后原样恢复”。

与现有出口的区别：

- 全量导出：所有会话 → 一个 DeepSeek 兼容 ZIP；不保留分组/扩展字段；用于兼容和迁移
- 合并导出：选中的组 → 一个虚拟组；保留 extras 和扩展字段，但组边界合并；用于分享/交付
- 完整备份：保留所有组、颜色、extras、摘要、系统提示词、引用/思考状态、附件原件，以及应用级设置；只用于本应用恢复

完整备份会包含高于组层级的设置（例如语言、主题、侧边栏状态、自动检查更新），所以恢复时不可避免是覆盖性的。建议：

- 单独放在“备份与恢复”入口，不混在普通导入里
- 恢复采用**整体替换**语义：先确认“将覆盖当前本地数据”，再清空并恢复；不做部分合并
- 需要保留当前数据时，先导出/备份现有数据
- 备份格式带版本号、manifest 和迁移逻辑；应用版本过旧时拒绝恢复
- 与“删除所有数据”对应设计：删除清空哪些数据，完整备份就应覆盖哪些数据；设置是否全部恢复需要单独列出

工作量主要在格式版本、恢复事务和设置覆盖确认。建议等组批量管理稳定后再做，不阻塞当前导出改进。
